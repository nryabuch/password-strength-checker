This sends only the first 5 characters of your password's SHA-1 hash to the Have I Been Pwned API (k-anonymity). Your full password and full hash never leave your browser. How this works ↓

How the breach check works, without leaking your password

  1. 01 / hash locally your password gets hashed with SHA-1, right in your browser, using the Web Crypto API. The plaintext never touches the network.
  2. 02 / truncate we only keep the first 5 characters of that hash.
  3. 03 / query those 5 characters get sent to the HIBP API. It sends back every hash suffix in its database that starts with that prefix, usually a few hundred of them.
  4. 04 / match locally your browser checks if your full hash suffix shows up in that list. The actual match happens on your machine, not on HIBP's server.

This is the same k-anonymity model HIBP's own client tools use. It's a real privacy-preserving pattern, not just a workaround.

What "entropy" and "bits" actually mean

Entropy is just a measure of how many guesses it'd take to land on your exact password by brute force. Each "bit" doubles the number of possible passwords an attacker has to try, so 10 bits means 1,024 possibilities, 40 bits means about a trillion, and so on. More bits means more randomness, and more randomness means it takes longer to crack.

Where the number comes from: we look at the character set you actually used (lowercase, uppercase, numbers, symbols) and your password's length, then calculate length × log2(character set size). A longer password with a mixed character set racks up bits fast. A long password using only lowercase letters can still score lower than a short one that mixes in symbols and numbers, because the character set matters as much as the length.

For crack time, we take that entropy number and figure out the total pool of possible passwords, which is 2 raised to the power of the entropy. Then we assume an attacker can try 10 billion guesses a second (a standard benchmark for an offline attack against a fast hash) and divide the pool by that guess rate. On average an attacker finds a password somewhere in the middle of the search space rather than at the very end, so we divide by 2 again to land on a realistic average-case estimate.

One honest caveat: that 10 billion guesses/sec number assumes a fast hash, or no hashing at all. A site using something slow on purpose, like bcrypt or Argon2, would push real crack times out dramatically further. Treat this number as a conservative worst-case, not a universal truth.
